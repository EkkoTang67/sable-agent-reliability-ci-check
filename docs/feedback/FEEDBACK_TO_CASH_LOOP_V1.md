# Feedback-to-Cash Loop v1.0

Status: ACTIVE — minimum viable operating rule  
Budget: 0  
System of record: GitHub Issues + this repository's version history  
Purpose: convert real usage evidence into product, distribution, and payment decisions without adding a paid platform.

## 1. The loop

`DISTRIBUTE → OBSERVE → QUALIFY EVIDENCE → DECIDE → CHANGE ONE THING → DISTRIBUTE AGAIN`

A comment, star, install, successful task, buyer conversation, and settled payment are different signals. Never report one as another.

## 2. Feedback event record

For each useful feedback event, retain the following in the issue or weekly review note:

- **Event/source:** issue URL, channel, date, and product version when known.
- **User job:** what the person was trying to accomplish.
- **Observed result:** what actually happened; include a reproducible minimal example when safe.
- **Evidence status:** FACT / INFERENCE / UNKNOWN / DISPROVEN.
- **Failure or friction:** the specific point where work stopped or output became unusable.
- **Commercial signal:** none / exploratory interest / specific paid-scope question / identified buyer and payer / payable now / paid and settled.
- **Decision:** fix / test / hold / reject, with one-sentence reason.
- **Next check:** one low-cost, falsifiable action and the evidence that would change our decision.

Do not record unnecessary personal data. Public issue forms must not invite confidential procurement documents or account credentials.

## 3. Evidence hierarchy

1. **Attention:** view, star, like, mention. Measures visibility only.
2. **Activation:** install or run. Measures initial action only.
3. **Verified use:** a real task and output checked against a current authoritative source.
4. **Repeated value:** different users or repeated tasks show the same useful outcome.
5. **Commercial intent:** a defined problem, scope, price discussion, and an identifiable buyer/payer. Intent is still not payment.
6. **R3:** a lawful, authorized stranger-buyer transaction with verifiable funds actually settled into the user's controlled account.

Do not infer conversion rates from missing denominators. Do not infer willingness to pay from compliments or installs.

## 4. Operating cadence

- **Immediately:** triage reproducible high-impact extraction errors, especially eligibility, deadlines, fees/bonds, cancellation/update status, and payment/acceptance terms.
- **Weekly, maximum 15 minutes:** review new issues and any observed distribution or buyer event; classify evidence; choose at most one product/distribution experiment; write a short decision note.
- **At the end of each experiment:** record the denominator, observed events, limitations, and continue/change/stop decision. If there is no measurement, record UNKNOWN rather than claim success.
- **Monthly:** check whether real use and buyer evidence are moving toward payment. If attention grows but verified use or payer access does not, change the target or stop the channel rather than adding features by default.

## 5. Experiment template

- **Hypothesis:** One testable sentence.
- **Target user and current event:** Who has what task now?
- **Change:** One change only.
- **Cost ceiling:** 0 unless the user explicitly approves otherwise after a credible payment path is established.
- **Observation window:** Set before the test; don't extend it merely to avoid a negative result.
- **Denominator:** How many real exposures, visits, installs, or tasks were observed? State unknown when not measurable.
- **Success condition:** An observable user action or verified outcome, not a vanity metric.
- **Stop/change condition:** Evidence that would falsify the hypothesis.
- **Result:** FACT / INFERENCE / UNKNOWN / DISPROVEN.
- **Decision and reusable asset:** What changed and what can be reused next time?

## 6. Current China Tender Notice Extractor Lite tests

Primary question: Does evidence-linked extraction from a public Chinese procurement notice help a real user make a decision faster or avoid a material omission?

Track, without inventing data:

- installs or attempts observed, if measurable;
- real public-notice tasks reported;
- outputs independently checked;
- high-impact errors and time/date confusion;
- users who need the deeper GO / PARK / KILL / UNKNOWN decision;
- specific scope/price questions from potential buyers;
- actual paid and settled transactions.

The Lite skill deliberately extracts facts; it does not itself produce a final eligibility or investment decision. Feedback requesting that deeper decision is useful demand evidence, but not proof of payment.

## 7. Privacy and authority

- Do not add hidden telemetry or collect personal data merely to inflate analytics.
- Do not ask users to publish private tenders, personal information, credentials, bid documents, or customer secrets.
- Use public official URLs and minimal redacted excerpts where possible.
- A report submitted in an issue is evidence of a report, not independent proof that the claim is true.
- Do not change product licensing to satisfy a directory's submission rules without explicitly reviewing and approving the rights change.
- No paid browser automation, paid directory, hosting, ads, or tooling is required for this loop.

## 8. Decision rule

Every review ends with one of these states:

- **CONTINUE:** current evidence supports the next small test.
- **CHANGE:** a specific observed failure falsified part of the current approach.
- **PARK:** value may exist, but buyer, evidence, or timing is still unknown.
- **KILL:** evidence shows the target or distribution path fails the commercial gate.
- **R3 VERIFIED:** funds have actually settled and the transaction evidence is checkable.

The objective is not to keep the project alive. It is to make the next economic decision better using the fewest moving parts.
